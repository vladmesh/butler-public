# Butler — спецификация MVP

Внешний агент-дворецкий: принимает голосовухи владельца в Telegram, отвечает текстом,
имеет полные полномочия на этой машине и по SSH. Наблюдает за пайплайном секретаря,
но НЕ является его частью: ничего в этом репо не должно зависеть от работоспособности
диспетчера, Orca или `secretary reconcile`. Единственные допустимые точки касания
секретаря — memory-mcp (read), CLI `secretary ...` (изнутри головы) и симлинки скиллов.

Все дизайн-решения зафиксированы гриллингом 2026-08-13 (12 пунктов, см. DESIGN.md).
Этот файл — имплементационная спека каркаса.

## 1. Общая схема

```
Telegram (voice/text от владельца)
   │ long-poll (aiogram)
   ▼
butler-bridge (вечный systemd-сервис, python)
   │ 1. проверить from_id == ADMIN_ID, иначе молча игнор
   │ 2. voice → скачать ogg → транскрипция Groq (фоллбек OpenRouter)
   │ 3. выбрать голову: probe claude-sub → claude; красный → probe openai-sub → codex
   │ 4. спавн головы (subprocess) с resume прошлой сессии
   │ 5. stdout головы → нарезать по 4096 → отправить в чат
   ▼
голова: claude -p --resume <sid>  |  codex exec resume <sid>
   (полные права, memory-mcp, скиллы, SSH)
```

Мост тупой и минимальный: никакой логики задач, только транспорт + транскрипция +
спавн. Весь интеллект — в голове (персона PERSONA.md + скиллы).

## 3. Конфиг (.env)

```
BUTLER_TG_TOKEN=            # токен бота от BotFather
BUTLER_ADMIN_ID=            # telegram id владельца (см. TELEGRAM_ID_ADMIN у секретаря)
GROQ_API_KEY=               # free tier, транскрипция
OPENROUTER_API_KEY=         # фоллбек транскрипции (опционально; нет ключа → фоллбек выключен)
BUTLER_WORKDIR=/home/dev/butler
BUTLER_CLAUDE_MODEL=opus
BUTLER_CLAUDE_EFFORT=medium
BUTLER_CODEX_MODEL=gpt-5.6-terra
BUTLER_CODEX_EFFORT=high
BUTLER_SESSION_MAX_TURNS=    # ротация сессии по числу успешных тёрнов (по умолчанию 40)
BUTLER_SESSION_MAX_AGE_H=    # ротация сессии по возрасту в часах (по умолчанию 48)
BUTLER_HEAD_TIMEOUT_S=900   # жёсткий таймаут одного тёрна головы
BUTLER_SERVICE_TURN_TIMEOUT_S=300  # свой предел служебного тёрна перед ротацией (§4.8)
BUTLER_SHUTDOWN_GRACE_S=300 # сколько ждать идущий тёрн при остановке (§4.9); TimeoutStopSec выше
BUTLER_STT_LANGUAGE=ru      # язык распознавания; пусто → автоопределение провайдером
BUTLER_STT_PROMPT=...       # доменный словарь терминов владельца (только Groq); пусто → не уходит
BUTLER_STT_GROQ_MODEL=whisper-large-v3-turbo
BUTLER_STT_OPENROUTER_MODEL=openai/whisper-large-v3-turbo
```

`config.py` при старте валидирует обязательные поля (TG_TOKEN, ADMIN_ID, GROQ_API_KEY)
и падает с внятной ошибкой, если их нет. Никаких дефолтов для секретов.

Параметры распознавания секретами не являются и все необязательны: без них мост работает
как раньше (turbo-модели, язык и словарь не передаются). Смена модели или словаря — правка
`.env` и рестарт, без выкатки новой версии моста.

## 4. Мост: поведение по шагам

### 4.1 Приём сообщения
- aiogram 3.x, long polling (никаких вебхуков — нет входящих портов).
- Хэндлер на `Message`. Если `message.from_user.id != ADMIN_ID` — return без ответа
  и без логирования содержимого (только counter в лог).
- Поддерживаемые типы: `voice`, `audio`, `text`. Остальные (фото, документы) —
  вежливый ответ «пока умею только голос и текст» (этап 2 — прокинуть файлы голове).
- На voice сразу отправить реакцию/`typing`-статус, чтобы было видно, что услышал.

### 4.2 Транскрипция (`transcribe.py`)
- Скачать voice-файл (ogg/opus) во временный файл.
- POST в Groq `audio/transcriptions`, model из `BUTLER_STT_GROQ_MODEL`, формат ogg
  отправляется как есть (Groq принимает ogg/opus напрямую, перекодировка не нужна).
- Язык (`BUTLER_STT_LANGUAGE`) уходит в запрос к обоим провайдерам; пустое значение =
  параметр не передаётся вообще, то есть возврат к автоопределению.
- Доменный словарь (`BUTLER_STT_PROMPT`) уходит только в Groq: OpenAI-совместимый
  multipart-эндпоинт OpenRouter `prompt` принимает, но игнорирует
  (https://openrouter.ai/docs/guides/overview/multimodal/stt), поэтому в фолбэк он не
  отправляется — иначе мёртвый параметр выглядел бы работающим.
- Параметры каждого запроса пишутся в лог событием `transcribe_request` (провайдер,
  модель, язык, клипнутый словарь); у фолбэка поле словаря пустое, как и сам запрос.
- Ошибка/таймаут (>15s) → повтор 1 раз → OpenRouter (`BUTLER_STT_OPENROUTER_MODEL`),
  если ключ задан → иначе ответ владельцу «транскрипция лежит: <причина>».
- Транскрипт префиксуется в промпт головы строкой:
  `[voice transcript, может содержать ошибки распознавания]`.

### 4.3 Выбор головы (`heads.py`)
- Probe в духе `health.resolve_head` секретаря, но своя минимальная реализация
  (НЕ импортировать код секретаря — только паттерн):
  - claude: `claude -p --model haiku "ok"` с таймаутом 30s, exit 0 и непустой stdout → зелёный.
  - codex: `codex exec -m gpt-5.4-mini "say ok"` аналогично.
- Кэш результата probe в памяти процесса с TTL 300s (не гонять токен на каждое сообщение).
- Порядок: claude зелёный → claude; иначе codex зелёный → codex; оба красные →
  ответ владельцу «обе подписки красные, попробуй позже» (без OpenRouter-фоллбека головы в MVP).

### 4.4 Спавн головы
- claude:
  `claude -p --model $BUTLER_CLAUDE_MODEL --effort $BUTLER_CLAUDE_EFFORT --dangerously-skip-permissions --resume <sid> <prompt>`
  - cwd = BUTLER_WORKDIR; персона едет в `--append-system-prompt` на каждом вызове,
    включая `--resume` (системный промпт не конкурирует с содержимым разговора).
  - Первый запуск (нет sid): без `--resume`, из вывода забрать session id
    (`--output-format json` отдаёт `session_id`) и сохранить в `state/sessions.json`.
- codex:
  `codex exec resume <sid> <prompt>` / первый раз `codex exec <prompt>`,
  `-m $BUTLER_CODEX_MODEL`, effort через `-c model_reasoning_effort="high"`,
  full-auto режим (`--dangerously-bypass-approvals-and-sandbox` или эквивалент,
  проверить актуальный флаг), CODEX_HOME не трогать — использовать дефолтный логин.
  - Флага системного промпта у `codex exec` нет, поэтому персона едет текстом внутри
    промпта — каждый тёрн, resume включительно, — обёрнутая маркерами
    `=== ПЕРСОНА ... === КОНЕЦ ПЕРСОНЫ ===`, чтобы голова не приняла её за реплику
    владельца. Отправленная один раз, персона живёт в истории обычной репликой и
    уходит первой при сжатии контекста, поэтому повтор обязателен.
- Персона перечитывается с диска на каждом тёрне: правка `persona/PERSONA.md` доезжает
  со следующего сообщения, без перезапуска моста и без новой сессии. Пустая,
  отсутствующая или нечитаемая персона — предупреждение `persona_missing` в логе,
  тёрн при этом идёт как обычно.
- Таймаут тёрна BUTLER_HEAD_TIMEOUT_S: по истечении убить процесс-группу,
  ответить «голова думала слишком долго и была убита, лог: <path>».
- stderr головы — в лог моста, владельцу не слать.
- Пустой stdout при exit 0 → один ретрай, затем честное сообщение об ошибке.
- Ответ головы, если >4096 символов — нарезать по границам строк, слать частями.
- Конкурентность: обрабатываем строго по одному сообщению за раз (asyncio.Lock).
  Новые сообщения во время работы головы — в очередь; если в очереди уже ≥3 —
  ответить «я ещё думаю над прошлым».

### 4.5 Смена головы посреди диалога
- Если резюмим claude-сессию, а claude красный → спавним codex БЕЗ resume клодового
  контекста, но с преамбулой: «Продолжаем диалог, прошлый контекст утерян из-за смены
  головы», а следом — хвост из `state/history.jsonl`.
- Для этого мост пишет краткую историю: `state/history.jsonl`, по строке на реплику
  `{"ts", "who": "owner|butler", "text": <усечено до 500 симв>}`. Файл не подрезается:
  его опустошает только ротация (§4.7), которая сначала складывает всё в архив. В преамбулу
  идёт хвост (последние 10 реплик) и содержимое `state/digest.md`, если файл есть и непуст.
- **Хвост подан не как «последние сообщения», а разделённым по тому, закрыт разговор или
  нет.** До последней реплики butler'а включительно — блок `УЖЕ ОТВЕЧЕННАЯ ИСТОРИЯ`
  («ответы уже ушли, заново отвечать не надо»); всё, что после неё, — блок `БЕЗ ОТВЕТА`
  (тёрн умер, мост остановили посреди него). Само сообщение владельца, ради которого
  тёрн идёт, отделено на другом конце склейки заголовком `ТЕКУЩЕЕ СООБЩЕНИЕ ВЛАДЕЛЬЦА`
  и стоит последним. Маркеры появляются только там, где есть преамбула: резюмнутая
  сессия видит свою историю своим контекстом, а служебный тёрн (§4.8) — вообще не
  владелец.
- Разделение — не украшение промпта, а починенный баг: 20.08.2026 преемник ротированной
  сессии получил хвост, в котором лежали и вопрос владельца, и уже ушедший ответ на него,
  плюс короткое «Тест» промптом, — и вместо ответа на «Тест» слово в слово повторил
  ответ трёхминутной давности. Голова выбрала самый заметный «незакрытый» вопрос,
  потому что в склейке ничто не говорило, какой из них закрыт.

### 4.6 Один канал наружу в течение тёрна (`outbox.py` + `bin/butler-say`)
Голова может ответить владельцу, не дожидаясь конца тёрна: долгая работа, запущенная
джоба, найденный промежуточный результат. Это намеренный вызов, а не трансляция stdout —
владелец видит то, что голова решила сказать.

**Весь текст, который владелец видит в рамках тёрна, идёт через одну упорядоченную
очередь `Outbox`**: промежуточные сообщения головы, финальный ответ и служебные строки о
срыве (таймаут, ненулевой выход, пустая голова). Финальный ответ ставится в ту же очередь
последним, а не отправляется отдельно. Пока путей наружу было два, порядок между ними был
политикой, которую надо помнить в каждой ветке кода, и он ломался там, где о ней забыли;
теперь порядок — свойство очереди.

- Сообщения различаются по происхождению: имя файла служебной строки моста заканчивается
  на `-bridge` (`bin/butler-say` такого не пишет, `Outbox.send` — тоже: финальный ответ
  это диалог). Признак едет вместе с сообщением до доставки и решает ровно одно:
  **`history.jsonl` — это диалог владельца и головы, служебной строке моста там не
  место.** Отсюда две вещи. Голова, которая ничего не сказала, ретраится и объявляется
  пустой, даже если владельцу уже ушла строка моста: своя строка не делает голову менее
  молчаливой. И доставка служебной строки не записывает сообщение владельца — иначе
  строка о ротации, ушедшая пока служебный тёрн ещё идёт (§4.8), положила бы сообщение
  в историю перед ротацией, та бы его заархивировала, и преемник получил бы его дважды:
  цитатой в преамбуле и своим промптом.
- Мост на каждый тёрн заводит `state/outbox/<turn-id>/` и отдаёт путь голове переменной
  `BUTLER_OUTBOX_DIR`. Окружение процесса головы передаётся явно: унаследованное плюс эта
  переменная (`run_process(..., env=...)`), остальное не затирается.
- Голова пишет сообщение командой `bin/butler-say "текст"` (или текстом в stdin).
  Команда — stdlib-only скрипт под системным `python3`: ни `aiogram`, ни `httpx`, ни
  `butler_bridge` она не импортирует. Пустой текст, отсутствующая переменная или
  несуществующий каталог — ненулевой выход и внятная строка в stderr. Мост кладёт своё
  в ту же очередь методом `Outbox.send()` — по тем же правилам.
- Запись атомарна: временный файл плюс `rename` в `<time_ns>-<rand>.msg`, поэтому мост
  не прочитает половину сообщения. Имя начинается с наносекундной метки, поэтому
  сортировка по имени = порядок отправки.
- Порядок постановки в очередь = порядок доставки = порядок записи в `history.jsonl`:
  единственный, кто отправляет владельцу и пишет реплику `butler`, — это разбор очереди.
- Инвариант, который держит `Outbox` (а не вызывающий код): **сообщение, попавшее в
  очередь, либо доставлено, либо осознанно брошено с записью в лог; висеть оно не
  остаётся и не существует только внутри отменяемой корутины.** Отсюда правила: файл
  удаляется только после того, как отправка вернулась; опрос останавливается кооперативно
  (`settle`), а не отменой задачи посреди отправки; сбойное сообщение держит очередь за
  собой; сворачивание разбирает очередь до конца (`deliver_all`), а не делает одну
  попытку; каталог с недоставленным сообщением не удаляется.
- Сворачивание тёрна — одна точка `settle()` в порядке: остановить опрос → дождаться
  отправки, которая может быть в полёте → разобрать очередь до конца. Голова к этому
  моменту мертва, новых сообщений не будет, поэтому очередь пуста — и финальный ответ,
  поставленный после, последний по построению, а не по договорённости.
- Отказ транспорта: сообщение остаётся файлом и повторяется (до 3 попыток, пауза 0.5s),
  задерживая всё, что за ним, — порядок важнее пропускной способности; после трёх отказов
  оно выбрасывается с `outbox_message_dropped`, чтобы не держать очередь весь тёрн.
- Каталог привязан к тёрну: имя уникально, по завершении тёрна каталог удаляется, а на
  старте следующего чужие каталоги подметаются. Сообщение убитого тёрна не доедет.
  Тёрн, снятый снаружи посреди отправки, — единственный путь, которому разрешено оставить
  сообщение файлом (`outbox_left_undelivered`) вместо того, чтобы его потерять; подметает
  такой каталог следующий тёрн.
- Финальный ответ не дублирует уже отправленное: текст, совпавший с одним из
  промежуточных сообщений, в очередь не ставится.
- Пустой финал после промежуточных сообщений — это не молчание: владелец уже отвечен,
  ретрая головы и служебной строки про пустой ответ не будет. Если не было ни
  сообщений, ни ответа — прежнее поведение (§4.4: один ретрай, затем честная ошибка).
- Срыв тёрна (падение, `BUTLER_HEAD_TIMEOUT_S`) не отменяет уже отправленного: владелец
  получает его, а затем — служебную строку о срыве с путём к логу, из той же очереди.
- Единственное исключение, где прямая отправка остаётся: голова вообще не запускалась —
  обе подписки красные или транскрипция упала до тёрна. Очереди в этом тёрне не
  существует, обгонять нечего.

### 4.7 Ротация сессии
- У сессии головы в `sessions.json` есть момент старта и число прошедших тёрнов; тёрн
  засчитывается только успешный, там же, где голова забирает владение диалогом.
- Два независимых порога из `.env`: `BUTLER_SESSION_MAX_TURNS` (40) и
  `BUTLER_SESSION_MAX_AGE_H` (48), возраст считается от старта сессии. Сработал любой —
  сессия уходит в ротацию. 0 или меньше выключает порог.
- Решение принимается в `run_head`, до спавна головы: история целиком уезжает в
  `state/archive/<date>-<sid>.jsonl`, рабочий `history.jsonl` остаётся пустым, id сессии
  сбрасывается. Следующий запуск идёт без `--resume` и получает преамбулу тем же
  механизмом, что и смена головы. Сообщение владельца пишется в историю позже, поэтому
  ротация не может ни заархивировать его, ни задвоить.
- Долг преемника durable, а не «на один запуск»: ротация кладёт в `sessions.json` ключ
  `pending_preamble` с хвостом истории, каким он был до архивации. Пока ключ на месте,
  каждый следующий запуск (ретрай внутри тёрна, новый тёрн после сбоя, смена головы,
  рестарт юнита) строит преамбулу из него плюс того, что диалог сказал после ротации.
  Снимает ключ только `State.activate` в момент, когда записан новый `session_id`, то есть
  когда преемник действительно ответил.


### 4.8 Служебный тёрн перед ротацией
Ротация обрывает контекст, и всё, что сессия знала и не записала, пропадает вместе с ней.
Поэтому перед `rotate_session` в старую сессию уходит ровно один служебный тёрн — с её
`session_id`, то есть с резюмом: это последний момент, когда весь контекст диалога ещё
собран в одном месте.

- Что он делает, задаётся его промптом (`SERVICE_TURN_PROMPT`), а не кодом: переписать
  `state/digest.md` под текущее положение дел, вынести долгоиграющие факты через
  `secretary memory` (`commit` для «запомни» владельца, `propose` для своих выводов) и
  дописать привычки в секцию `## Выучено` персоны отдельным git-коммитом. Мост его только
  запускает и проверяет, что он оставил после себя.
- Владельцу он не пишет: `BUTLER_OUTBOX_DIR` уходит в него пустым, поэтому
  `bin/butler-say` отказывается работать, а его финальный текст никуда не отправляется —
  он нужен только как признак того, что тёрн не пустой. Отвечать владельцу — не его роль.
  Это закрытый путь по умолчанию, а не изоляция: тёрн — наша же голова с нашим же
  промптом, с теми же правами на машину, что даёт ей персона, и подставить путь к живой
  очереди она при желании может. От своей головы мы тут не защищаемся; закрывается
  ровно та осечка, которая реальна, — привычка позвать `butler-say`, которой учит персона.
- Свой предел времени `BUTLER_SERVICE_TURN_TIMEOUT_S` (300s), заметно меньше
  `BUTLER_HEAD_TIMEOUT_S`: тёрн стоит между сообщением владельца и ответом на него.
  Чтобы это не выглядело зависшим ботом, мост перед ним кладёт в очередь тёрна свою
  строку «переношу контекст в новую сессию» — по правилам §4.6, а не мимо очереди.
  Строка называет длину молчания, посчитанную из самого предела, поэтому поднятый
  предел не превращает обещание в неправду, сказанную перед более долгой паузой.
  Считается вверх и вместе с дренажем: `ceil((предел + DRAIN_AFTER_KILL_S)/60)`. Предел
  не обязан быть кратным минуте, а на том самом пути, ради которого строка и пишется,
  тёрн убивают по таймауту и ещё до `DRAIN_AFTER_KILL_S` секунд дочитывают его трубы —
  округление к ближайшему обещало бы 5 минут при молчании в 5 минут 10 секунд. Обещание,
  которое ломается ровно там, где нужно, хуже чуть завышенного.
- Предел измерен, а не подобран. Удавшиеся переносы по журналу моста
  (`service_turn_spawn` → `service_turn_done`): 104 с (14.08), 126 с (15.08), 141 с
  (20.08, `digest.md` 19389 байт); сорвавшийся 20.08 не уложился в прежние 180 с и увёл
  ротацию в отсрочку, а владельца — в четырёхминутное ожидание ответа. Тёрн растёт
  вместе с дайджестом, который переписывает, поэтому 141 с под пределом 180 с — это не
  запас, а следующий таймаут; 300 с чуть больше двойного от самого долгого удавшегося.
  Слишком низкий предел дороже слишком высокого: таймаут стоит владельцу всего ожидания
  и оставляет ротацию несделанной, так что следующее сообщение платит за неё снова.
  Чтобы следующий пересмотр читал числа, а не разности меток времени в логе,
  `service_turn_done` несёт `duration_s`.
- Контрактная часть персоны неприкосновенна, и это проверка в коде
  (`persona_guard.guard_persona`), а не пожелание в промпте. Файл делится позиционно:
  всё до первой строки, побайтово равной `## Выучено`, — контракт, от неё до конца —
  секция. Маркер с хвостовым пробелом или лишним `#` секцию не открывает: он читается
  как пропавшая секция, а не как секция чуть иначе. Сравнение контракта тоже побайтовое,
  вплоть до хвостовых переводов строки — иначе правка была бы, а уведомления нет. После тёрна
  файл переписывается как старый контракт плюс новая секция, поэтому контракт байт-в-байт
  прежний по построению. Правка контракта, пропавшая или сломанная секция, исчезнувший
  файл — состояние чинится целиком из старого файла, и владелец получает об этом строку.
- Сторож стоит на **каждом** выходе из служебного тёрна, а не на удачном: он в `finally`,
  поэтому отработает и когда мост останавливают посреди тёрна (`Butler.stop()` отменяет
  воркер, отмена проходит сквозь `run_head`). Чтобы сторож смотрел на окончательный файл,
  `run_process` на `CancelledError` убивает группу процессов и пожинает её до того, как
  отмена уйдёт наружу: голова не дописывает персону после того, как мост ушёл.
- Уведомление о починке персоны — durable: строка кладётся в `sessions.json`
  (`pending_notices`) и уходит владельцу первым делом на ближайшем тёрне, у которого есть
  outbox (`flush_notices` в начале `run_head`). В обычном случае это тот же тёрн, сразу
  после служебного; на отмене — следующий, потому что очередь умирающего тёрна всё равно
  будет сметена недоставленной. Из состояния строка изымается только когда есть куда её
  положить, поэтому «сказать не успели» не превращается в «не сказали».
- Сбой (таймаут, launch_error, ненулевой выход, пустой ответ) ротацию **откладывает**:
  сессия остаётся живой, история не тронута, владелец получает и строку о сбое, и обычный
  ответ на своё сообщение из той же сессии. Следующее сообщение пробует снова.
- Чтобы «не ротируем» не превратилось в вечно растущую сессию, серия сбоев считается в
  `sessions.json` (`service_failures`, durable — переживает рестарт). Первый и второй
  сбой подряд откладывают ротацию, третий (`SERVICE_TURN_ATTEMPTS`) ротирует сессию без
  служебного тёрна: история целиком уезжает в архив, хвост — в `pending_preamble`, то
  есть диалог не теряется и в этой ветке; пропадает только незаписанный дайджест.
  Счётчик обнуляется на успешном служебном тёрне и на любой состоявшейся ротации.
- Сообщение владельца ротация по-прежнему не может ни задвоить, ни потерять: оно
  пишется в историю при первой доставке владельцу **реплики диалога** (§4.6), а строка
  моста о ротации таковой не является. Служебный тёрн заведомо длиннее интервала опроса
  очереди, поэтому эта строка уходит владельцу до `rotate_session` — и не тянет за собой
  сообщение владельца в историю, которую ротация вот-вот заархивирует.
- Служебный тёрн не «засчитывается»: `State.activate` в нём не вызывается, поэтому он не
  меняет ни счётчик тёрнов, ни владение диалогом, ни `pending_preamble`.

### 4.9 Остановка моста (SIGTERM)
`systemctl --user restart butler.service` приходит в живой мост посреди тёрна. Отмена
воркера здесь не годится: `run_process` по `CancelledError` синхронно бьёт группу
процессов головы SIGKILL'ом, и почти собранный ответ не доезжает до владельца. Поэтому
штатная остановка идёт мимо отмены, а отмена остаётся аварийным путём.

- SIGTERM и SIGINT ловит `loop.add_signal_handler` (`bot.install_stop_signals`);
  у aiogram своя обработка сигналов выключена (`handle_signals=False`).
- Обработчик делает ровно одно, что нельзя отложить: `Butler.begin_closing()` — приём
  закрыт. Всё остальное требует await и живёт в обычном async-коде, который ждёт флага.
- Приём закрыт — значит `admit` отказывает, и владелец слышит не «я ещё думаю над
  прошлым», а строку про перезапуск: ждать бесполезно, повторить через минуту — да.
- Поллинг останавливается штатно (`dispatcher.stop_polling`), но сессия бота остаётся
  открытой (`close_bot_session=False`): идущему тёрну ещё есть что через неё сказать.
- Инвариант остановки: ни один апдейт, за который aiogram уже взялся, не остаётся
  неучтённым к моменту закрытия сессии бота. aiogram запускает каждый апдейт отдельной
  задачей и не ждёт их, когда поллинг встал, поэтому дренаж спрашивает два набора сразу:
  - `_handle_update_tasks` самого aiogram, взятый защитно (`in_flight_updates`,
    `getattr` по приватному имени). Это единственный учёт, который знает про апдейт с
    момента его появления: `_polling` кладёт задачу в набор синхронно, сразу за
    `create_task`, до её первого шага. Реестр из тел обработчиков это окно не покрывает
    по построению — задачи создаёт не мост, и пустой реестр не отличим от «ещё не
    зарегистрировался». Приватное имя держит не комментарий, а тест
    (`test_aiogram_registers_the_update_task_when_it_creates_it`): апгрейд aiogram,
    который это сломает, обязан ронять суиту, а не тихо возвращать потерю сообщений.
  - собственный реестр `Butler.handling()` — перекрёстная проверка и единственное, что
    знает про обработчик, уже сидящий внутри отправки.
  Набора у aiogram нет вовсе (getattr вернул None) — это не «всё чисто»: в лог уходит
  `shutdown_handlers_unknown`, а не молчаливое признание полёта пустым.
- `Butler.drain_handlers(dispatcher)` ждёт опустошения объединения обоих наборов с
  собственной короткой границей `HANDLER_DRAIN_S` (10 с, константа в коде, а не
  переменная `.env`: обработчик только шлёт строку); истекла — `shutdown_handlers_forced`
  в лог и отмена, как и у тёрна.
- `handle_as_tasks` остаётся дефолтным (`True`). Выключить его — не починка: тогда
  обработчик исполняется внутри задачи поллинга, которую aiogram на остановке отменяет
  как pending, и вместо неучтённого обработчика выходит отменённый на полуслове.
- Порядок в `run()` один и живёт в `wind_down()`: остановить поллинг → дождаться своих
  обработчиков → `Butler.close(grace)` → и только потом закрыть сессию бота. Закрытие
  сессии — последнее действие, после которого сказать уже нечего.
- `Butler.close(grace_s)` кладёт в очередь сентинел — *за* идущим тёрном, никогда перед
  ним, — и ждёт воркера с верхней границей `BUTLER_SHUTDOWN_GRACE_S` (300 с). Дошёл
  воркер до сентинела — тёрн договорил, ответ ушёл, в лог идёт `shutdown_done`.
- Порог истёк — `shutdown_forced` в лог (это и есть отличимая строка о принудительном
  завершении), воркер отменяется, `run_process` убивает голову. Владельцу пишется долг
  через `push_notice`: тёрн не успел договорить.
- То, что осталось в очереди на момент сигнала, не начинается и не теряется молча:
  `close` вынимает его и записывает одну строку долга через `push_notice`. Она уезжает
  владельцу первой строкой первого тёрна после перезапуска (`flush_notices`, §4.8).
  Иначе говоря, каждое сообщение либо получает ответ до выхода, либо владелец узнаёт,
  что ответа не будет.

## 5. systemd (`packaging/butler.service`)

User-unit (`systemctl --user`), по образцу секретарских юнитов:
```
[Unit]
Description=Butler telegram bridge
After=network-online.target

[Service]
Type=simple
WorkingDirectory=/home/dev/butler
EnvironmentFile=/home/dev/butler/.env
ExecStart=/home/dev/butler/.venv/bin/python -m butler_bridge
Restart=always
RestartSec=5
TimeoutStopSec=330

[Install]
WantedBy=default.target
```
Юнит держит один процесс, но запуск мимо него (руками, отладочный прогон, второй юнит)
дал бы двух поллеров на одном токене и гонку за `state/`. Поэтому единственность
обеспечивает сам процесс: сразу после `load_config()`, до `ensure_dirs()` и до создания
`Butler`, он берёт эксклюзивный неблокирующий `flock` на `state/butler.lock` и держит
дескриптор открытым всю жизнь (`butler_bridge/singleton.py`). В файл пишется pid
владельца — для чтения логов, не для решения о владении: решает только замок, и ядро
снимает его на любом завершении, включая SIGKILL, так что чистить нечего. Второй
экземпляр при живом первом пишет `singleton_busy` с pid владельца и выходит с кодом 3,
не тронув ни одного файла в `state/` и не создав `Bot`.

Владельца называет ядро, а не файл. Взять замок и записать в файл pid — две операции,
слить их в одну атомарную нельзя, поэтому любой ответ, вычитанный из файла, — догадка:
файл может быть пуст, может хранить номер пережитого владельца, а сам по себе pid
доказывает лишь, что процесс с таким номером существует, но не что он держит этот замок.
`/proc/locks` свободен и от того, и от другого: строка есть ровно пока замок держат, и pid
в ней — держателя. Поэтому единственный источник владельца для строки лога — ответ ядра,
сопоставленный с файлом по `st_dev`/`st_ino` (`parse_proc_locks`); ни ожидания, ни порога,
ни проверки живости не нужно. Содержимое файла замка не читает никто: pid внутри — только
удобство для человека, открывшего файл руками. Если `/proc/locks` недоступен или строки по
паре устройство+inode в нём нет, лог пишет `owner_pid=unattributed why=…`; отказ второго
экземпляра от этого не зависит — замок не взят, значит выход с кодом 3.

README описывает установку: `python -m venv .venv && .venv/bin/pip install -e .`,
`cp .env.example .env`, заполнить, `systemctl --user enable --now butler` (симлинк юнита
в `~/.config/systemd/user/`). Никакого участия `secretary reconcile`.

## 6. Логи
- stdout моста → journald (стандартно для systemd). Формат: одна строка на событие,
  `ts level event key=value`. События: msg_in, transcribed, head_spawn, head_done,
  head_fail, probe, persona_missing, outbox_sent, outbox_final_duplicate, outbox_sweep,
  outbox_deliver_fail, outbox_message_dropped, outbox_left_undelivered, outbox_pump_fail,
  service_turn_spawn, service_turn_done, service_turn_persona_repaired,
  service_turn_notice_lost, rotation_deferred, rotation_forced, singleton_busy,
  shutdown_signal, shutdown_admission_closed, shutdown_queue_dropped, shutdown_done,
  shutdown_forced, shutdown_handlers_waiting, shutdown_handlers_forced,
  shutdown_handlers_unknown.
  Текст сообщений владельца в лог НЕ писать целиком (первые 80 симв);
  текст промежуточных сообщений головы — тоже, `outbox_sent` несёт только размер и номер.
- `head_spawn` несёт признак персоны: `persona_chars` и `persona_sha` (первые 8 символов
  sha256) — по двум строкам лога видно, уехала старая персона или новая. Сам текст
  персоны в лог не пишется.

## 7. Персона головы (`persona/PERSONA.md`)

Написать по-русски. Содержание:
- Ты — butler, личный дворецкий владельца (vladmesh), канал — telegram, вход — голос,
  твой выход — текст. Отвечай коротко: это чат, а не отчёт. Без воды и заголовков.
- Транскрипт может врать: если команда звучит странно или опасно — переспроси.
- Полномочия: полные на этой машине и по SSH (алиасы в ~/.ssh/config: site, codegen).
- Протокол подтверждения: необратимое или наружу (деплой, удаление данных, рестарт
  прод-сервисов, force-push, траты) → сначала переспросить одним сообщением. Остальное
  (статусы, спринты, карточки, пинки пайплайна, прогон меги) — делать молча.
- Память: memory-mcp на чтение; «запомни: ...» от владельца → `secretary memory commit`
  напрямую (actor butler); собственные выводы → `secretary memory propose`.
- Секретарь: статусы через `secretary status`, `secretary sprint ...`, доска Kanboard.
  Ты наблюдатель с правами, но не часть пайплайна — не претендуй на его карточки.
- Сообщение посреди тёрна: `bin/butler-say "текст"` из рабочего каталога — когда работа
  затянулась, когда запущена джоба, когда найден промежуточный результат. Владелец видит
  их сразу и по порядку; финальный ответ не повторяет уже сказанное (§4.6). Это не лента
  размышлений: одно-два сообщения за долгий тёрн.
- Долгие джобы: запускать detached (`systemd-run --user` локально, nohup по ssh),
  хэндл писать в `state/jobs/active/<name>.json` ({cmd, host, log, started}), сразу
  отвечать владельцу через `bin/butler-say` что запущено и где лог.
- Эскалация: если задача сложная (архитектура, гриллинг, разбор инцидента) или владелец
  прямо просит — скажи владельцу, что стоит перезапуститься на fable/sol medium.
